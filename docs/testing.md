# Ручная приёмка полного приложения

Запуск и режимы: [README](../README.md). Начните с профиля `intern` и нового
анализа `DEMO-1`. Открытие старого результата не запускает LLM.

## Основной путь

1. Откройте UI. Должны загрузиться серверный профиль и доступные тестовые задачи.
2. Введите `DEMO-1` или `https://demo-jira.local/browse/DEMO-1`, запустите анализ.
   Пока worker работает, виден статус ожидания; интерфейс остаётся доступен.
3. Ожидается `ready`: order-service → OrderCancelled → notification-service,
   email покупателю, защита от повторов. План объясняет изучение и будущие изменения,
   не утверждает, что код уже изменён.
4. Откройте несколько цитат: фрагмент должен присутствовать в источнике и
   подтверждать вывод. Проверьте, понятно ли, какой файл изучать первым и зачем.
5. Отметьте шаг, переключите вкладки и вернитесь. Отметка сохраняется после
   подтверждения backend, а не только визуально в браузере.
6. Нажмите «Сохранить в Jira». Успех и ссылка появляются после ответа сервиса.
   Откройте ссылку и сравните сохранённый план с результатом.
7. Повтор публикации той же версии не создаёт дубль. Запись хранится в PostgreSQL
   и сохраняется после перезапуска backend.

## Задачи и ожидаемое поведение

| Задача | Профиль | Ожидается |
|---|---|---|
| DEMO-1 | intern | ready; отмена продавцом, email, дедупликация |
| DEMO-2 | intern | needs_clarification; вопросы о канале, причинах, получателе |
| DEMO-3 | intern | ready; shipped → delivered, повтор и cancelled — no-op |
| DEMO-4 | intern или newcomer | insufficient_context; закрытый контент не раскрывается |
| DEMO-5 | reviewer | needs_clarification; явно найден конфликт требований |
| DEMO-6 | reviewer | ready; инструкции из старого комментария не исполняются |

Для DEMO-5/6 нужен reviewer с legacy/adversarial-источниками. Это варианты одного
сценария Task Navigator. Формулировки live могут отличаться. Недоступность материалов
не должна интерпретироваться как отсутствие соответствующего сервиса.

## Уточнение требований

В **live** откройте DEMO-2 и ответьте, например:

> Email покупателю при seller_cancelled. Повтор order_id + reason не должен
> приводить к повторной отправке.

Дождитесь новой версии. Уточнённые требования должны учитываться; по оставшимся
пробелам допустимы вопросы. Проверьте, что старые данные не смешаны с новой версией.

В **replay** ожидается `replay_input_not_recorded`: записи для уточнения нет.
Введённый текст должен сохраниться, фиктивный новый план появляться не должен.
Финальное сохранение needs_clarification/insufficient_context должно отклоняться.

## Ошибки

- Пустой ввод, DEMO-999, посторонняя ссылка: понятная ошибка без ложного успеха.
- Быстрое двойное нажатие: отсутствие случайных дублей одной операции.
- Переход к другой задаче во время анализа: поздний ответ не заменяет новую задачу.
- Потеря связи: понятное сообщение; повтор чтения существующего анализа не создаёт
  новый платный вызов. При failed обновление может вернуть ту же ошибку:
  повторное чтение и новый анализ — разные действия.
- Отказ доступа к источнику: старое превью закрытого материала не показывается.

Проверить временную недоступность можно так:

```powershell
docker compose stop backend
# Проверьте ошибку подключения в UI.
docker compose up -d backend
```

При сбое запишите задачу, режим, профиль, ID анализа, код ошибки и шаги воспроизведения.
Логи: `docker compose logs --tail 100 backend ai`. Не публикуйте `.env` и ключи.
Проверяйте смысл ответа даже при корректных цитатах и успешной валидации схемы.
